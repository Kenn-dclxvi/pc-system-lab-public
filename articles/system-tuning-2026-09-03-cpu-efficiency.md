# 最適なコア数を探すところから、FF14で使う電力を選ぶところへ

前回のCPU・BIOS編では、Core i9-10900Kの高い倍率をどこまで残せるかを調べ、1～2コア時は5.2 GHz、3コア時は5.1 GHz、4～10コア時は5.0 GHzという形までたどり着きました。

次に残っていたのは、5.1 GHzと5.2 GHzの短時間確認、それから5.0 GHzの長時間確認です。そこで問題がなければ、高性能側の基本形は完成するはずでした。

ただ、その前に気になることがありました。

**そもそも、4KのFF14ベンチは10900Kの何を必要としているのか。**

高性能側の確認を続ける前に、まず相手の性質を知りたくなりました。そこで先にFF14ベンチそのものを分析し、コア数、クロック、キャッシュ、メモリのどこが効きそうかを整理しました。

考えを広げて整理するときはChatGPTと話し、実機で確かめる段階ではCodexに測定と記録を組んでもらいました。結果が出れば、今度はその結果から次に何を試すかを考える。この往復によって、最初は想像もしていなかった方向へ話が進んでいきます。

## まず、FF14がCPUの何を使うのか

FF14のCPU性能について調べると、最初に浮かんだのは「6物理コア付近までは性能へ効き、その先はコア数より実効クロックやキャッシュ、メモリの影響が大きくなるのではないか」という仮説でした。

10900Kは、BIOSで有効コア数を減らしても20 MBのL3キャッシュが残ります。ならば10コア全部を高く回すより、6コアと20 MB L3を残したまま、その6コアを高く回した方がFF14には合うかもしれません。

Ringも候補には挙がりました。ただ、私の環境では43倍より上を安定させた記憶がなく、Coreやメモリと一緒に触ると原因の切り分けも難しくなります。まずコア数とCore Clockを調べ、Ringは最後に効果を確かめることにしました。

最初に試したのは、使用中のコア数に応じて上限倍率を変える`By Core Usage`です。

| 倍率表 | Score | 実際の主な動作 |
| --- | ---: | --- |
| 1～4コア51倍 / 5～10コア50倍 | 17,534 | 全10コアで50倍 |
| 1～2コア52倍 / 3～6コア51倍 / 7～8コア49倍 / 9～10コア48倍 | 17,349 | 48倍が支配的 |
| 1～4コア52倍 / 5～10コア50倍 | 17,497 | 50倍が支配的 |

ここで分かったのは、`1～4コア52倍`が特定の4コアを52倍で動かす設定ではないことです。同時に使われているコアが4個以下のときだけ、52倍へ入れます。

FF14中は平均9.97個の物理コアが稼働中と判定されていました。だから少数コア側の倍率を上げても、ベンチ中は10コア側の倍率が選ばれます。

計測処理自身がコア数を増やしている可能性も疑い、監視処理をFF14が強く使う論理プロセッサから離し、取得間隔と集計負荷も見直しました。それでも、多くの物理コアへ仕事が広がる傾向は残りました。

倍率表だけでは、狙った6コア高クロックを試せない。

では、物理コアそのものを6個にすればどうなるのか。

## 6コアにしたら、52倍を本当に使わせられた

BIOSで有効コア数を6へ減らすと、Windows上では6コア12スレッドになり、L3キャッシュは20 MBのまま残りました。これなら全コアが動いても6コア時の倍率が選ばれます。

最初の6コア52倍ではDirectXエラーも出ましたが、その表示だけでCPUが原因とは決めず、確認を続けました。その後の完走結果を50倍、10コア構成と並べると、こうなりました。

| 構成 | Score |
| --- | ---: |
| 6コア52倍 | 17,854 |
| 6コア50倍 | 17,662 |
| 10コア50倍 | 17,721 |

6コア52倍は、確かに今回の中で最も高いScoreです。ただ、6コア50倍との差は192、率にして約1.1%でした。6コアを5.2 GHzで動かせるようにしても、伸びは思ったより小さい。

せっかく10700から10900Kへ替えたのに、突き詰めたら6コアCPUとして使うのか、と少し笑ってしまいました。ただ、コア数まで変えて狙いどおり52倍を使わせたからこそ、高倍率を攻略すること自体には大きな意味がなさそうだと分かりました。

この時点で「ワッパ的にはいいかも」とも考えました。ただ、この手動比較には電力記録がありません。効率が良いと確認したわけではなく、まだ思いつきの段階です。

で、次にやったことはもっと単純でした。上を詰めるより、下でどこからがくんと下がるかを見る方が楽しい。そう思って、6コアのまま倍率を下げ始めました。

最初は50倍から46倍へ一気に下げました。それでもScoreは17,485です。400 MHz下げても177しか変わらなかったので、間の48倍を測ると17,622。さらに44倍へ下げても17,347でした。

| 6コア設定 | Score |
| ---: | ---: |
| 52倍 | 17,854 |
| 50倍 | 17,662 |
| 48倍 | 17,622 |
| 46倍 | 17,485 |
| 44倍 | 17,347 |
| 43倍 | 17,278 |
| 42倍 | 17,048 |
| 40倍 | 16,795 |

5.2 GHzから4.6 GHzまで下げても、Scoreの低下は約2%です。ここまで性能が残るとは、始める前には分かっていませんでした。4KではGPUがボトルネックになりやすいと言われますが、このPCでもCPUクロックの差が全体性能へ出にくいことを実測できました。

低い解像度ならCPU差はもっと見えやすくなります。ただ、私が実際に使うのは4Kです。CPU単体の差を大きく見せるためだけに、使わない解像度へ変えるつもりはありませんでした。

44倍の次は40倍まで下げ、Scoreは16,795でした。さすがにこのあたりまでかな、と思える下がり方です。ただ、44倍から40倍まで一度に飛ばしているので、どこから変化が大きくなったのかはまだ分かりません。

その途中で、Core Clockを下げた分だけRingを上げられないかも試しました。コア44倍のままRingを43倍から45倍へ上げると、Scoreは17,347から17,317へ下がりました。少なくともこの条件では伸びが見えなかったため、Ringは43倍へ戻しています。

そこで40倍と44倍の間を埋めました。42倍は17,048、43倍は17,278です。44倍から43倍では69の低下でしたが、43倍から42倍では230下がりました。下げた結果を並べてみると、6コアではScoreの低下が大きくなり始める境目が43倍と42倍の間にありそうです。

ここまで来ると、同じ43倍を10コアへ戻したらどうなるのかも見たくなりました。まずは、その違いを知りたいだけの比較です。

## 10コアへ戻すと、もっと低いクロックでも性能が残った

10コア43倍のScoreは17,387でした。6コア43倍の17,278との差は109です。50倍での6コアと10コアの差は59だったので、小さいながらも差が広がりました。

ここで初めて、低い倍率では追加の4コアが効いてくる可能性が見えてきました。10コアはFF14以外の普段使いでも残したいので、次は10コアのまま42倍、41倍、40倍と下げ、その先で37倍まで確かめました。

| 10コア設定 | Score | Minimum FPS |
| ---: | ---: | ---: |
| 50倍 | 17,721 | 未記録 |
| 43倍 | 17,387 | 未記録 |
| 42倍 | 17,249 | 未記録 |
| 41倍 | 17,234 | 未記録 |
| 40倍 | 17,174 | 69 |
| 37倍 | 16,797 | 64 |

42倍は17,249、41倍は17,234で、その差はわずか15でした。40倍でも17,174、Minimum 69 FPSです。同じ42倍では6コアが17,048、10コアが17,249。同じ40倍では6コアが16,795、10コアが17,174でした。

高クロック側ではほとんど差がなかった追加の4コアが、クロックを下げると並列性で補うようになりました。10900Kの10コアは、最高Scoreを大きく伸ばすためではなく、低いクロックでも性能を保つために効いています。

どこまで残るのかが気になって、最後は定格倍率の37倍まで下げました。それでもScore 16,797、Minimum 64 FPSです。ここまで下げた方が10コアの特性がよく見えるとは、まったく想像していませんでした。

クロック当たりScoreだけなら37倍が最も高く見えます。ただ、これはCPU単体の一般的な効率ではなく、10900KとRTX 3080で4KのFF14を動かしたときに、3.7 GHzでもこの絶対性能が残ったという話です。

映像を見ていても、40倍では違和感がありませんでした。Score 17,174、Minimum 69 FPSなら、体感差が出そうだと考えていた60 FPSも上回っています。

そこで、まず10コア40倍を実用候補として残しました。問題が出るまでは、これ以上下げる理由も、上げ直す理由もありません。

ここで、最初に浮かんでいた性能/Wの話が具体的な試験目標になりました。ただ、手動のScoreだけでは電力が分かりません。

40倍なら、性能を残しながら電力をどこまで減らせるのか。

## 電力を測ると、性能/Wは狙い以上だった

10コア40倍を倍率表へ入れ、標準のセンサー記録を使ってFF14を測りました。1～9コア側は高い倍率を残し、10コア使うときだけ40倍へ落とします。

このときの倍率表は、1～4コア52倍、5コア51倍、6コア50倍、7コア49倍、8コア48倍、9コア47倍、10コア40倍です。中間を1倍ずつ分けたのは、あとで通常操作のどの領域が使われたかを見分けるためでした。

高クロック構成と比べた結果は、想像以上にはっきりしていました。

| 指標 | 高クロック構成 | 10コア時40倍 | 変化 |
| --- | ---: | ---: | ---: |
| Score | 17,611 | 16,871 | -4.20% |
| CPU Package平均電力 | 95.21 W | 55.83 W | -41.36% |
| 観測CPU+GPU平均電力 | 350.44 W | 310.06 W | -11.52% |
| Score / CPU Package平均W | 184.97 | 302.17 | +63.36% |
| Score / 観測CPU+GPU平均W | 50.25 | 54.41 | +8.28% |

Scoreは4.20%下がりました。一方、CPU Package平均電力は約40 W減っています。GPUを含む観測電力で見ても、1 W当たりのScoreは8.28%上がりました。

ここで初めて、40倍は「低いから効率が良さそう」ではなく、電力まで含めてワット当たり性能が良いと確認できました。狙いどおりというより、狙っていた以上です。

高性能を目指して始めたCPU調整は、この結果で性能/Wを選ぶ話へはっきり変わりました。

ただし、全コア40倍を常用すればよいわけではありません。FF14以外では、少数コアの高いクロックが操作の応答性に効く可能性があります。

次の疑問は、40倍をFF14へ使いながら、普段使いの速さも残せるかでした。

## FF14用の40倍と、普段使いの52倍を一つの表にした

先に決めた役割は単純です。

- 1～9コアは、普段の操作に使う高クロック側
- 10コアは、FF14で持続的に使う性能/W重視の40倍

でも、役割を考えただけでは実際の使われ方に合うか分かりません。そのために作ったのが、先ほどの1倍刻みの倍率表です。倍率そのものを目印にして、ブラウザ操作中に何個の物理コアが動くかを250 msごとに調べました。

通常操作全体では、動いた物理コア数の中央値が6、90%が9コア以下でした。10コアへ入る場面もありましたが、平均343 ms、最大781 msの短い動作です。FF14のように10コア領域へ居続ける負荷とは違います。

これで、1～9コアへ普段使いの性能を残し、持続的に10コアを使うFF14だけ40倍へ落とす考え方は、実際の使われ方とも合っていると判断しました。

中間の1倍刻みは観測のための設定で、最終形ではありません。以前の構成で5～10コア50倍が動いており、全コア51倍でもFF14を完走していたため、5～9コアは50倍へ揃えました。

| 同時に使うコア数 | 上限倍率 | 役割 |
| --- | ---: | --- |
| 1～4コア | 52倍 | 軽い処理の応答性を残す |
| 5～9コア | 50倍 | 通常操作と中間負荷の性能を残す |
| 10コア | 40倍 | FF14の性能/Wを重視する |

先に段階的な表で挙動を見たから、想像だけで中間倍率をまとめずに済みました。PC全体の使い方を考えながら、実際に見極める動作点を52倍、50倍、40倍の三つへ減らした形です。

この表でFF14を測ると、Score 16,888、Average 117.9506 FPS、Minimum 66 FPSでした。直前の段階的な設定と比べても目立った劣化はありません。ベンチ中は引き続き10コア40倍が中心でした。

これで、FF14側の効率点と普段使い側の高クロックを一つの倍率表へ入れられました。

ようやく、最初にやるつもりだった電圧調整へ戻ります。

## 全体の電圧を下げると、短時間と長時間で答えが変わった

最初はCPU全体の電圧を同じ量だけ下げる`Offset Mode`を使いました。

`-25 mV`では、FF14中の40倍Vcore中央値が1.189932 Vから1.163292 Vへ約26.6 mV下がり、CPU Package平均電力も53.96 Wから52.45 Wへ下がりました。Score 16,927、Minimum 66 FPSで完走しています。

設定した下げ幅が実際のVcoreへ反映され、性能も保てる。それなら、もう少し下げたくなります。

`-100 mV`では単発試験中にDirectXエラーが出ました。このときはCPUだけでなく、GPUが0.850 Vで1935 MHzまで上がっていたことも気になりました。そこでGPU側の設定クロックを下げて切り分け、単発は完走しましたが、長時間ループは約28分で予期しない再起動となりました。

再起動後にはGPU timeout系の記録とCPU WHEAの両方が残り、原因を一つへ絞れませんでした。だから、`-100 mV`を安定設定にはできません。

次の`-80 mV`は3時間51分31秒動きました。ただ、開始から1時間46分59秒後にCPUの訂正済みWHEAが1件発生しています。画面が落ちず、ベンチが動き続けても、これは合格にはできません。

`-60 mV`へ20 mV戻すと、少なくとも3時間33分54秒動作し、WHEA、再起動、アプリケーション停止は0件でした。

これで、CPU全体を同じだけ下げるなら、`-60 mV`が現在の倍率表に対する安定側の基準になりました。

ただ、FF14中に長く使うのは40倍です。50倍や52倍は短時間しか使いません。必要な電圧の余裕まで同じとは限りません。

全体を一律に下げる段階はここで終え、倍率帯ごとに分けることにしました。

## 個別調整の材料として、WHEA発生時の倍率を追った

個別調整へ進むと決めたあと、これまでのVIDとVcoreを倍率ごとに整理しました。

VIDはCPUが要求している電圧、Vcoreはマザーボード側で観測した共有の供給電圧です。中央値だけでも、最大値だけでも決められません。同じ時刻の倍率、VID、Vcore、負荷状態を合わせ、WHEAの前後で何が起きていたかを見ました。

`-80 mV`でWHEAが記録された306.961 ms後の測定点では、Core 0が40倍、Core 1～9が50倍でした。さらに少し後の標準センサー記録ではGPU使用率が0%です。

ここで初めて、40倍でFF14本編を動かし続ける場面より、ループが切り替わって50倍へ戻る瞬間の方が電圧の余裕が少なかった可能性が出てきました。

この1件だけで50倍が原因だとは決められません。ただ、一律`-80 mV`を全倍率へ掛けるより、40倍側では下げ幅を残し、高倍率側へ行くほど余裕を戻す方が筋は通ります。

そこで全体offsetを外し、CPU Core/Cache Voltageは`Auto`のまま、V/F Pointごとに下げ幅を分けました。

| 周波数帯 | V/F Point設定 | 考え方 |
| --- | ---: | --- |
| 40倍付近 | Point 3 / 4: -80 mV | 長く使う効率重視の領域 |
| 50倍付近 | Point 5 / 6: -60 mV | 全体-60 mVで長時間動いた余裕を戻す |
| 52倍付近 | Point 7: -40 mV | 測定が少ないため、さらに余裕を持たせる |
| 曲線の両端 | Point 1 / 2 / 8: Auto | 根拠の薄い領域は動かさない |

52倍はFF14本編ではほとんど使わないため、別の短時間負荷を作って直接確かめました。P-Core 2で52倍の有効な測定点を48件取得し、実クロックは約5.2 GHz、WHEAは0件でした。Point 7は未確認から短時間確認済みへ進みましたが、15秒の試験なので長時間の余裕までは分かりません。

通常操作の約2秒間隔の記録には52倍が出ていませんでした。一方、HWiNFOの最大履歴には5.2 GHzが残っています。

つまり、52倍を使わないのではありません。一定間隔の記録では拾えない短い動作として使われていた、と考えるのが自然です。回数や滞在時間は分からなくても、Point 7を無関係な領域として消してはいけないことは分かりました。

倍率ごとの電圧曲線はできました。

次は、これをどこまで下げられるかではなく、実際に使ううえで何を上限にするかです。

## 50倍へ戻る瞬間を狙い、90 Wの上限を入れた

50倍へ上がる場面を意図的に作るため、5つの物理コアへ2秒の負荷と2秒の休止を15回繰り返しました。

電力制限なしではWHEAは出なかったものの、Vcore最大1.491855 V、CPU Package Power最大107.814 W、CPU温度最大89℃を観測しました。

直ちに故障を意味する値ではありません。ただ、不要な電力を減らすために作った設定なのに、短い遷移だけ100 Wを超えるのは方向が合いません。

IntelのPL1 125 Wを使う案も考えましたが、今回の107.814 Wでは制限が掛かりません。そこで長時間・短時間の電力上限をどちらも90 Wにし、CPU Core/Cache Current Limit Maxは245 Aにしました。

同じ50倍遷移試験をもう一度行うと、結果は次のように変わりました。

| 指標 | 電力制限なし | 90 W制限 |
| --- | ---: | ---: |
| CPU Package Power最大 | 107.814 W | 81.175 W |
| CPU温度最大 | 89℃ | 78℃ |
| Vcore最大 | 1.491855 V | 1.456334 V |
| Vcore 1.45 V以上の割合 | 63.2% | 8.9% |
| WHEA | 0 | 0 |

上位6コアの実効クロックは約5.4%下がりました。90 W制限は無料の安全策ではなく、重いCPU負荷では性能と引き換えに電力と熱を抑える設定です。また、Vcoreそのものを1.45 V以下に固定するものでもありません。

それでも、今回抑えたかった短時間の高電力は明確に減りました。

あとは、この組み合わせが既知のWHEA発生時間を越えられるかです。

## 既知の失敗時間を越え、公式結果を一つ残した

長時間試験の目標は、理由なく3時間や4時間にしたわけではありません。`-80 mV`でWHEAが出るまでの最長記録が1時間46分59秒だったため、まずそこを越えることを合格の目安にしました。

現在のV/F Point曲線と90 W / 245 A設定では、FF14の長時間ループを2時間6分35.884秒続けています。既知のWHEA時刻を約19分37秒越え、その間のWHEA、GPUやWindows、アプリケーションの異常を示すイベントは0件でした。

GPU負荷中のCPU Package Powerは平均54.21 W、最大83.2 W。CPU温度は平均60.94℃、最大70℃、Vcore最大は1.394174 Vでした。電力上限も意図どおり作動しています。

長時間試験を終えたところで、最新のBIOS設定による公式ベンチマーク結果がまだ一つもないことに気づきました。そこで最後に、同じ設定で単発試験を行いました。

![FF14黄金のレガシーベンチマーク Score 16,841](./images/ffxiv-dawntrail-benchmark-score-16841.png)

結果画面が「カスタム」になっているのは、DLSSを全域へ適用しているためです。私の使い方では、必要なパフォーマンスを出しながらGPU負荷と消費電力を下げる方が大事なので、実際に使う環境へ合わせてこの設定を選んでいます。

結果はScore 16,841、Average 117.6512 FPS、Minimum 64 FPS、評価は「非常に快適」でした。

90 W制限を入れる前と比べても、Scoreに大きな劣化はありませんでした。今回のFF14では、性能をほぼ保ったまま電力上限を加えられています。

これが最高Scoreだったわけではありません。最高は6コア52倍の17,854です。

それでも、この画像を到達点にしたい理由があります。

FF14が必要とするCPU性能を調べ、6コア高クロックを実際に試し、今度は下方向へ測って10コア40倍の価値を見つけました。普段使いの52倍、50倍と一つの表へまとめ、電圧を倍率帯ごとに分け、最後に電力上限を加えています。

**Score 16,841は、その一連の判断を通って現在の基本設定へ到達した証跡です。**

## 現在の基本形

| 設定 | 採用値 |
| --- | --- |
| CPU倍率 | 1～4コア52倍 / 5～9コア50倍 / 10コア40倍 |
| CPU Core/Cache Voltage | Auto、全体offsetなし |
| V/F Point 1 / 2 | Auto |
| V/F Point 3 / 4 | -80 mV |
| V/F Point 5 / 6 | -60 mV |
| V/F Point 7 | -40 mV |
| V/F Point 8 | Auto |
| PL1 / PL2 | 90 W / 90 W |
| CPU Core/Cache Current Limit Max | 245 A |
| Cache Ratio | 43倍 |
| TVB Voltage Optimizations | Enabled |
| Overclocking TVB | Disabled |

最初は、5.1 GHzと5.2 GHzを確認して5.0 GHzの長時間試験を行い、高性能側を完成させるつもりでした。

でも、FF14ベンチを分析したことで「何コアを、どこまで速くすればよいのか」という疑問が生まれました。6コアで上を試したから下を見たくなり、下げたから10コアの意味が見え、電力を測ったから性能/Wを選べるようになりました。

ChatGPTとの考察とCodexによる測定は、別々の作業ではなく、この疑問を次へつなぐ往復でした。昔は可変倍率と電圧の組み合わせを前に諦めていた調整を、考えたことと実際に起きたことへ分けながら、ここまで追えるようになったのが一番大きいと思います。

ただ、完成したのは現在の基本形です。電圧の限界探しは終わっていません。

- 各V/F Pointの最小安定電圧は確定していません。
- 52倍の専用確認は短時間で、Point 7単独の長時間余裕は不明です。
- 手動のコア数・倍率比較は多くが各1回で、電力記録もありません。
- 高クロック構成と10コア40倍の比較では、倍率表と`TVB Voltage Optimizations`が同時に変わっています。2条件とも各1回なので、差のすべてを40倍だけの効果とは扱えません。
- 観測CPU+GPU電力には、マザーボード、メモリ、ストレージ、ファン、ポンプ、電源変換損失は含まれていません。
- `-60 mV`長時間試験には約91分のセンサー記録欠落があります。
- 室温とRadiator Fan RPMは取得できていません。
- 90 W制限は、FF14よりCPU依存の強い処理では性能を下げる可能性があります。
- 今回見つけた値は、このPCで4KのFF14を動かした結果であり、別のCPU負荷へそのまま一般化はできません。

なので、次はしばらくこの設定を普段使いし、FF14以外も含めて異常や性能上の不満が出ないかを見ます。その先でもう一段詰めるなら、全体を一度に動かさず、対象のV/F Pointと負荷を一つずつ分けて確かめます。
