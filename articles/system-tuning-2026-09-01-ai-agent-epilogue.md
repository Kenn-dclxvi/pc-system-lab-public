# 5年前と一番違ったのは、PCではなかった

[← CPU・BIOS編](./system-tuning-2026-09-01-cpu-bios.md) / [索引](./system-tuning-2026-09-01-index.md)

ここまで、ケース冷却、GPU、CPU・BIOSの3本に分けて書きました。

使っているPCは、5年前に組んだCore i9-10900KとRTX 3080のマシンです。ASUSのBIOSにAdaptive VoltageやV/F Point、TVBが用意されていたのも当時から変わりません。

それでも、今回できたことは5年前とかなり違いました。

一番大きかったのは、AIエージェントを使って実験を進められたことだと思います。

## 5年前は、調べるだけでかなり重かった

10900Kを組んだ当時も、設定の意味を調べることはできました。

ただ、BIOSにはTurbo Ratio、TVB、SVID、Adaptive Voltage、Load-line Calibration、AC/DC Loadline、V/F Pointなど大量の項目があります。

ひとつずつ仕様を調べても、それぞれがどうつながって実際のクロックや電圧になるのかまで覚えて使い続けるのは大変でした。

結局、Manual 1.300 Vでスコアが出て、ゲームが安定して動けばいい、というところで止めています。

それは当時としては十分だったと思います。

今回も最初からAIへ全部任せたわけではありません。まずは設定の意味を聞き、実機で起きていることと照らし合わせるところから始めました。

ただ、途中からAIエージェントに実際の計測や整理まで任せるようになると、できることが一気に増えました。

## ケース編では、「設定したつもり」を毎回確認できた

Bottomファンの調整では、Fan Xpertの画面ではGPU温度連動になっているのに、実際のRPMは約900 RPMのままということがありました。

さらに、保存したファンプロファイルとASUS fan serviceが実際に使っている`FanStore.xml`が違う試験もありました。

ここで必要なのは、設定画面を見ることではなく、設定ファイルと実際のRPMを毎回突き合わせることです。

一度なら手でできます。

でも、カーブを変えるたび、再起動するたび、測定前後で同じ確認を繰り返すとなると面倒です。

今回はその確認をAIエージェントに任せられたので、「設定したつもり」で取ったデータをそのまま採用せずに済みました。

ケース編で変わったのは、冷却の知識より先に、こういう確認作業を普通の手順として入れられたことでした。

## GPU編では、「落ちた」で終わらなくなった

RTX 3080を1905 MHz / 825 mVにしたときは、DirectX Errorが出て、`nvlddmkm` Event ID 153とLiveKernelEvent 141が残りました。

850 mVへ戻すと短いFF14は通りましたが、長時間試験では59分03.988秒でBugCheck 0x50が発生しました。

その約12分前にはCPU/cache系のcorrected WHEAも出ています。

ここで、Windows Event Log、WHEAのRaw CPER、WinDbg、GPUドライバのイベント、温度ログを同じ時間帯で見比べました。

825 mVのときはGPUドライバの停止やリセットが見えている。一方、850 mVの長時間試験ではそのイベントがなく、先にCPU/cache側のWHEAが出ている。

原因を一つに決めることはできませんでした。

ただ、「825 mVと同じGPU側の失敗ではなさそう」というところまで切り分けられたので、850 mVをすぐ捨てず、次はCPU側を見ることにしました。

AIエージェントを使っていなければ、自分ならここまで毎回ログを追わず、「長時間だと落ちるから設定を戻す」で終わっていたかもしれません。

## CPU編では、繰り返し試験の量が変わった

CPU・BIOS編では、この差がもっと大きく出ました。

5.3 GHzがFF14で出ないと分かったあと、Preferred Coreだけで本当に出るのかを確認しました。

P-Core 2へ負荷を固定して5.3 GHzを確認し、次に非PreferredのP-Core 0 / 1 / 4～9を同じ方法で順番に試し、最後にP-Core 2をもう一度同じ条件で測りました。

これで、試験方法そのものが5.3 GHzを邪魔していたのではなく、Preferred Core側だけで出る挙動だと確認できました。

こういう試験も、人間だけでできます。

ただ、コアごとに負荷を変え、ログを保存し、Effective ClockやC0 Residencyを見て負荷が成立しているか確認し、WHEAを調べ、最後に設定を元へ戻すところまで毎回やると、趣味のPCとしてはかなり重いです。

AIエージェントへ繰り返し部分を任せられたことで、「5.3 GHzが出た」で終わらず、どの条件なら出るのかまで進めました。

V/F Pointの調整でも同じです。

Point 5 / 6を-40 mVにした長時間試験では、通常の監視だけで10,951 sample、CPU V/Fの記録は24,887 sampleありました。

人間でもCSVを開いて集計できます。

でも、倍率ごとのVIDとVcoreを分け、異常値を除外し、過去の固定1.300 Vや補正なしAdaptiveと比較して、その結果から次にどこを触るかを決める作業を何度も繰り返すのは大変です。

今回はその分析が短時間で返ってくるので、-30 mV、-40 mV、-50 mV、その後の5.0 GHz設定まで連続して試せました。

## AIに任せても、結果だけを受け取る感じにはならなかった

実際にやってみると、ログの集計や調査をAIへ任せても、結果だけを受け取る感じにはなりませんでした。

「なぜFF14では5.3 GHzが出ないのか」「VIDとVcoreは何が違うのか」「なぜ固定1.300 Vなのに実測Vcoreは約1.27 Vなのか」と、その場で起きたことに合わせて説明を聞けます。

仕様だけをまとめて読むより、実機の数字と結びつくので理解しやすい。

仕事では、先輩が何を見ているかを肩越しに見て覚えることが多かったです。どのログを最初に見るのか、何を異常と判断するのか、どこは無視するのかを見て覚えるやり方です。

今回のPCでは、その先輩が横にいなくても、「なぜそこを見るのか」をその場で聞きながら自分の実機で試せます。

この違いはかなり大きいと思います。

## ただ、AIの答えをそのまま設定にはしない

今回、AIエージェントを使ったからといって、AIが出した設定を正しいものとして採用したわけではありません。

実際、測ってみると予想と違ったことは何度もありました。

Rearを100%まで回してもほとんど冷えない。Bottomは止めてもほとんど変わらない。GPUの825 mVは落ちる。Overclocking TVB +1は全V/F PointをAutoへ戻してもWHEAが出る。

なので、設定を決める基準は最後まで実機の結果です。

AIエージェントには、情報を集めること、試験方法を作ること、ログを整理すること、過去の結果と比較することを任せます。

その結果を見て、次に何を試すか、どの設定を残すかは自分で決めます。

この分け方が、今回かなりうまく機能しました。

## 「気になるけど面倒だからやらない」が減った

今回の一連の調整を振り返ると、一番変わったのはここかもしれません。

5年前なら、5.3 GHzが出るコアを8個分試すとか、数時間分のVID / Vcoreを倍率別に集計するとか、WHEAのRaw CPERまで読むとか、できないわけではありません。

ただ、そこまでやる価値があるかと言われると、途中で「ゲームが動いているからもういいか」となっていたと思います。

今回は、その面倒なところをAIエージェントへ渡せます。

だから、疑問が出たときに試験まで進める回数が増えました。

AIO故障から始まった作業が、ケースファン、GPU、CPUのTVBとV/F Curveまで広がったのも、その影響が大きいと思います。

AIが答えを知っているからできた、というより、**調べて、測って、比べるための手間が下がったから、今までなら途中でやめていたところまで進めた**という感じです。

## 次も同じやり方で確認する

CPU側はまだ終わっていません。

次は、現在の`52 / 52 / 51 / 50 / 50 / 50 / 50 / 50`構成で5.1 GHz、5.2 GHz側の短時間試験を行い、そのあと5.0 GHzの長時間FF14を回す予定です。

そこでも、AIエージェントに計測と集計を任せ、実際のVcore、CPU Power、温度、WHEAを見て判断します。

5年前の10900Kで、まだどこまで詰められるのか。

もう少しこのやり方で続けてみたいと思います。
